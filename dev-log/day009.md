## Asynchronous Programming — Challenge 2 (completed)

Worked through scheduling multiple async calls. The key distinction that landed:

- `asyncio.gather(...)` runs coroutines concurrently and returns results in **submission order** (the order I passed them in).
- `asyncio.as_completed(...)` runs them concurrently too but yields each task **as it finishes** — so looping over it gives results in **completion order**.

Challenge 2 specifically asked for "the order of the execution," so I reached for `as_completed`, varied the sleep durations (tied to the numbers) so the tasks genuinely finished at different times, and looped:

```python
async def main():
    task1 = asyncio.create_task(sum(1, 2))
    task2 = asyncio.create_task(sum(3, 4))
    for task in asyncio.as_completed([task1, task2]):
        result = await task
        print(f"Result: {result}")
```

The `sum` coroutine had to `await asyncio.sleep(...)` **before** returning — my first drafts put the sleep *after* the `return`, where it never ran (dead code). Once the sleep moved above the return and its duration varied per call, the completion-order behaviour became observable.

Notably, the course's own "solution" used `gather` with equal sleep times — which doesn't actually demonstrate completion ordering at all. My `as_completed` version was more faithful to the stated problem than the provided answer.

## Mini Build 1 — Rock, Paper, Scissors (from scratch)

Built a round-based RPS game against a random computer choice. Iterated it several times:

- Started with a fixed 3 rounds and a long `if/elif` chain covering all six win/lose combinations.
- Added a user-chosen number of rounds, a running score, an `else` branch for invalid moves, and a final win/lose/tie verdict.
- Caught (and fixed) a scoring bug where a **loss** was awarding a point — the exact fragility that a six-branch hand-written chain invites.

Final version:

```python
import random

user_list = ["rock", "paper", "scissors"]
user_round_choice = input("How many rounds do you want to play? ")
user_score = 0

for i in range(int(user_round_choice)):
    print(f"Round {i + 1} of {user_round_choice}")
    user_choice = input("Enter your choice (rock, paper, scissors): ").lower()

    computer_choice = random.choice(user_list)

    print(f"\nYou chose {user_choice}, computer chose {computer_choice}.\n")

    if user_choice == computer_choice:
        print(f"Both players selected {user_choice}. It's a tie!")
    elif user_choice == "rock" and computer_choice == "scissors":
        print("Rock smashes scissors! You win!")
        user_score += 1
    elif user_choice == "scissors" and computer_choice == "rock":
        print("Rock smashes scissors! You lose.")
    elif user_choice == "paper" and computer_choice == "rock":
        print("Paper covers rock! You win!")
        user_score += 1
    elif user_choice == "rock" and computer_choice == "paper":
        print("Paper covers rock! You lose.")
    elif user_choice == "scissors" and computer_choice == "paper":
        print("Scissors cuts paper! You win!")
        user_score += 1
    elif user_choice == "paper" and computer_choice == "scissors":
        print("Scissors cuts paper! You lose.")
    else:
        print("Invalid input. Please choose rock, paper, or scissors.")

print(f"\nGame Over! Your final score is {user_score} out of {user_round_choice}.")

if user_score > int(user_round_choice) / 2:
    print("Congratulations! You won the game!")
elif user_score == int(user_round_choice) / 2:
    print("It's a tie!")
else:
    print("Sorry, you lost the game. Better luck next time!")
```

## Mini Build 2 — Rent / Budget Calculator (from scratch, refactored twice)

Built a student housing budget tool: split rent and utilities per person, convert student finance to a monthly figure, and compare against total monthly expenditure.

- **First version:** ten repeated `float(input(...))` blocks; no validation; a `Budget = Monthly_Budget` redundant copy.
- **Second version:** added currency-symbol stripping (`$`, `£`) — but copy-pasted that block **ten times**, making the file far more repetitive.
- **Third version — the refactor that mattered:** pulled the repeated input-and-convert logic into a single helper:

```python
def get_amount(prompt):
    value = input(prompt)
    value = value.replace("$", "").replace("£", "")
    return float(value)
```

Ten repetitive blocks collapsed into ten clean one-liners, and the symbol-stripping now lives in *one* place. Also normalised timescales so the comparison is honest — weekly food `* 4`, yearly travel pass `/ 12` — so everything is monthly before it's compared.

Final version:

```python
def get_amount(prompt):
    value = input(prompt)
    value = value.replace("$", "").replace("£", "")
    return float(value)

### Rent
Total_Rent = get_amount("Enter the Monthly rent amount: ")
Household = get_amount("Enter the number of people in the household: ")
Rent = Total_Rent / Household
Contract_length = get_amount("Enter the contract length in months: ")

### Utilities
Wifi = get_amount("Enter the Monthly wifi amount: ")
Electricity = get_amount("Enter the Monthly electricity amount: ")
Water = get_amount("Enter the Monthly water amount: ")
Gas = get_amount("Enter the Monthly gas amount: ")
Utilities = (Wifi + Electricity + Water + Gas) / Household

### Budget
Student_finance = get_amount("Enter your Student Finance Amount: ")
Budget = Student_finance / Contract_length

### Expenditure (normalised to monthly)
MonthlySubscriptions = get_amount("Enter your subscriptions amount for the month: ")
Weekly_Food = get_amount("Enter your food amount for the week: ")
Yearly_Travel_Pass = get_amount("Enter your travel amount for the year: ")
Monthly_Expenditure = (
    MonthlySubscriptions
    + Weekly_Food * 4
    + Yearly_Travel_Pass / 12
    + Rent
    + Utilities
)

### Breakdown
print("Your total Utilities is: ", Utilities)
print("Your total Rent is: ", Rent)
print("Your total Monthly Expenditure is: ", Monthly_Expenditure)
print("Your total Monthly budget is: ", Budget)

### Verdict
if Monthly_Expenditure > Budget:
    print("Warning: Your expenditure exceeds your budget! by", Monthly_Expenditure - Budget)
elif Budget > Monthly_Expenditure:
    print("You are within your budget. Remaining budget: ", Budget - Monthly_Expenditure)
else:
    print("Your expenditure is equal to your budget.")
```

# Programming Concepts Learned

Today I learned that:

- `asyncio.gather` returns results in **submission** order; `asyncio.as_completed` yields them in **completion** order. Choosing which you want is the actual skill, not a detail.
- `async` is about **concurrency, not parallelism** — much of asyncio runs on a single thread and gets its speedup by *overlapping the waiting*, not by using multiple CPU cores. Three 1-second tasks finish in ~1 second because the waits overlap.
- `await` marks a pause point where a coroutine yields control back to the event loop instead of blocking, freeing the loop to run other coroutines meanwhile.
- Modern async uses `asyncio.run(main())` — it creates the event loop, runs the coroutine, and closes the loop automatically, replacing the older `get_event_loop()` / `run_until_complete()` / `close()` dance.
- Any code after a `return` is **dead code** — it never runs. This bit me repeatedly in the async `sum` (sleep placed after the return did nothing). Not async-specific; plain Python worth burning in.
- Naming a function `sum` **shadows** the built-in `sum()`. Harmless in an exercise, avoid in real code.
- When the same line repeats many times (six win/lose branches; ten `float(input(...))` blocks), that's the signal to capture the pattern once — in a dict, or a helper function. Fewer places to get it wrong.
- Each RPS move beats exactly one other move, so the whole win/lose decision *could* collapse to one dict lookup (`beats = {"rock": "scissors", ...}`) instead of six branches — the same "find the rule, don't enumerate the cases" instinct as `gather` vs `as_completed`.
- A centralised input helper turns a dreaded ten-place validation job into a **one-place** fix — the payoff of refactoring before adding robustness.
- `string.templatelib` is real but **new in Python 3.14** — an unused autocomplete import didn't crash *because* I'm on 3.14.6; on earlier versions it would have. Version context changes what "will this crash" even means.

# Challenges

## Challenge 1 - The Sleep After the Return

### Problem

My async `sum` coroutine placed `await asyncio.sleep(...)` *after* `return n1 + n2`. The function returned instantly and never awaited anything, so both tasks finished at the same instant and no completion-ordering was observable — the whole point of the exercise was invisible.

### Solution

Moved the `sleep` *above* the return, and tied its duration to the inputs (`sleep(n1 + n2)`) so the two tasks finished at genuinely different times. Then `as_completed` had something real to order.

### Lesson Learned

Code after `return` never runs — it's dead code, and the interpreter won't always warn you. This same bug re-appeared across a couple of drafts before it stuck. A pause that never happens makes async code silently synchronous.

## Challenge 2 - Submission Order vs. Completion Order

### Problem

My first attempt awaited the tasks one at a time in a fixed sequence (`result1 = await task1; result2 = await task2`). That prints in the order I *wrote* them — submission order — which is the same thing Challenge 1's `gather` already did. It doesn't answer "in the order of execution."

### Solution

Replaced the manual sequential awaits with a loop over `asyncio.as_completed([task1, task2])`, awaiting each task as it was handed back. Now the print order follows whichever task *finishes* first, regardless of how they were listed.

### Lesson Learned

`gather` and `as_completed` look interchangeable until ordering matters. The moment the requirement is "as they complete," the manual-await approach quietly locks you into the wrong order. Worth noting: the course's provided solution didn't actually demonstrate this — "it runs and prints numbers" isn't the same as "it does what the prompt asked."

## Challenge 3 - The Scoring Bug Hidden in Six Branches

### Problem

In rock-paper-scissors, one of my six hand-written `elif` branches — paper vs. scissors — printed "You lose" but still did `user_score += 1`, awarding a point for a **loss**. It hid easily because you'd only notice if you happened to lose that exact matchup and watched the score tick up.

### Solution

Removed the erroneous `+= 1`. But the deeper fix is structural: because each move beats exactly one other move, the whole decision *could* live in a single dict lookup with **one** place deciding win vs. loss — making this class of bug impossible to reintroduce.

### Lesson Learned

Six near-identical branches is fragile by design — one wrong line disappears into the pile. The same "loop/logic in the wrong shape" theme from day008: when you find yourself enumerating every case by hand, there's usually an underlying rule to capture once instead.

## Challenge 5 - The Autocomplete Ghost Import

### Problem

`from string.templatelib import convert` appeared at the top of the calculator — a VS Code autocomplete suggestion I'd accepted without checking. `convert` is used nowhere. I assumed it would crash the program; it didn't.

### Solution

Left it flagged for deletion (it's dead clutter regardless). The reason it *didn't* crash: `string.templatelib` is brand new in Python 3.14, and I'm on 3.14.6 — so the import resolves. On any earlier version it would have thrown `ImportError`.

### Lesson Learned

Accepted-but-unused autocomplete suggestions are sticky — once in the file they look like they belong. Read what the recommender offers before tabbing it in. And "will this crash?" can depend on your Python version, so trust what actually runs on *your* setup over a confident claim about what *should* happen. (Good reminder to verify rather than assume — even against an AI.)

# Connection To My Final Goal

Async is directly load-bearing for the bot. Arbitrage is almost entirely **I/O-bound** — the program spends its time waiting on exchange API responses, not computing — which is exactly what async exists for. Polling several exchanges *concurrently* (via `gather`, or websockets on `asyncio`) is the difference between a screener reflecting the market *now* versus one perpetually seconds behind. The `as_completed` "react to whichever responds first" pattern maps straight onto processing whichever exchange returns first.

Honest caveats that surfaced today: async speeds up *waiting*, not computation, and it won't overcome rate limits or network distance to an exchange — those are the real latency bottlenecks, not my code. The arbitrage math itself is trivial CPU work that needs no async at all.
