## Generators Section (completed)

After the iterator classes, moved into generators, which use `yield` instead of a `return`. Built:

- Odd numbers from 1 to `n`
- Numbers counting down from `n` to 0
- **Fibonacci again — this time as a generator:**

```python
def fibbonaci(n):
    a, b = 0, 1
    for x in range(n):
        yield a
        a, b = b, a + b

for num in fibbonaci(10):
    print(num)
```

Building Fibonacci as a generator *right after* building it as a class was the most useful thing I did today. The generator does the same job with none of the boilerplate — no `__init__`, no `__iter__`, no `__next__`, no manual `StopIteration`, no counter stored on `self`. The `yield a` hands back one value and pauses; the next call resumes on the line after, with `a` and `b` still holding their values. When `range(n)` runs out, Python raises `StopIteration` for me automatically.

# Programming Concepts Learned

Today I learned that:

- An iterator class needs both `__iter__` (returns `self`) and `__next__` (returns the next single value, raises `StopIteration` when done). Missing or misnaming either breaks the protocol.
- `__next__` must be spelled with **double underscores**. A method named plain `next` is invisible to Python's iterator machinery — `for` loops and the built-in `next()` won't find it.
- The error "`__iter__` returned non-iterator type" specifically means the returned object has no `__next__` method — Python checks for it before accepting the object as an iterator.
- An iterator returns **one value per call** — the *caller* (a `for` loop, or `list()`) does the repeating. Putting a loop *inside* `__next__` that builds the whole result is the wrong shape.
- `list(SomeIterator(n))` consumes an iterator the same way a `for` loop does — calling `__next__` until `StopIteration` and collecting each value — so you can return single values from `__next__` and still get a list out.
- An iterator has to **remember state between calls** (values stored on `self`). Rebuilding a local variable inside `__next__` every call resets that state and defeats the purpose.
- Simultaneous assignment (`a, b = b, a + b`) evaluates the entire right-hand side using the *old* values before assigning, which is why the Fibonacci window-slide works as one line but would clobber itself as two separate lines.
- Generators (`yield`) are the same one-value-at-a-time behaviour as an iterator class, with the machinery collapsed away. `yield` pauses the function and resumes from that exact spot on the next call.
- Stopping on a **count** (a counter ticked down each call, or `range(n)`) is different from stopping on a **value** hitting a bound — Fibonacci needs count-based termination because the sequence sails right past any single target number.

# Challenges

## Challenge 1 - The Missing Double Underscores

### Problem

My DescNumbers class defined `def next(self)` instead of `def __next__(self)`. Calling `myrange.next()` directly appeared to work, which hid the problem — but a `for` loop over the object raised "`__iter__` returned non-iterator type."

### Solution

Renamed `next` to `__next__`. The direct call had only ever worked because I was calling a plain method by its literal name — it never went through Python's iterator protocol at all. The rename is what actually plugged the class into the machinery.

### Lesson Learned

"It works when I call it directly" is not the same as "it's a working iterator." Testing it the way it's *meant* to be used (a `for` loop) surfaced the bug that direct calls hid.

---

## Challenge 2 - The Two-Objects Loop & the Endpoint Off-by-One

### Problem

Two bugs in DescNumbers. First, I looped over one object but printed from a different one:

```python
myrange = DescNumbers(8)
for i in DescNumbers(8):      # a brand-new object
    print(myrange.next())     # pulls from the OLD object
```

Two separate countdowns running on two separate objects. Second, the decrement-before-return ordering dropped an endpoint — `DescNumbers(8)` started its output at 7 instead of 8.

### Solution

Collapsed the loop to a single object and printed the loop variable directly (`for i in DescNumbers(8): print(i)`) — the `for` loop already calls `__next__` and hands each value to `i`, so calling `.next()` manually inside was redundant. Fixed the endpoint by starting `current` one higher (`n + 1`).

### Lesson Learned

A `for` loop drives the iterator itself and gives you each value as the loop variable — you don't call `next` by hand inside it. And the same decrement-before-return off-by-one from the previous session's EvenNumbers showed up again here — except this time it dropped the *top* endpoint instead of the bottom, because the sequence counts down instead of up. Same bug shape, opposite end dropped. There are two ways to fix it: change the starting value, or change the order of the decrement and the return.

## Challenge 3 - "But It Works" — The Fake Fibonacci Iterator

### Problem

My first Fibonacci iterator built the entire sequence inside `__next__` with an inner `for` loop and returned the whole list every call:

```python
def __next__(self):
    myArray = [0, 1]
    for num in range(self.list - 2):
        ...
    return myArray
```

It looked like it worked. It didn't: it never raised `StopIteration` (so it ran forever), it returned a *list* instead of a single number (so it printed the whole list repeatedly instead of one number per line), and it rebuilt `myArray` from scratch every call so no state survived between calls. It was also only computing the right values by accident of negative indexing — fragile-right, not right.

### Solution

Rebuilt it as a real iterator: two values (`a`, `b`) stored on `self`, a `count` ticked down each call, `__next__` returning a single value and sliding the window with `self.a, self.b = self.b, self.a + self.b`:

```python
class Fibonacci:
    def __init__(self, n):
        self.count = n
        self.a = 0
        self.b = 1

    def __iter__(self):
        return self

    def __next__(self):
        if self.count <= 0:
            raise StopIteration
        value = self.a
        self.a, self.b = self.b, self.a + self.b
        self.count -= 1
        return value

print(list(Fibonacci(8)))   # [0, 1, 1, 2, 3, 5, 8, 13]
```

### Lesson Learned

This was the same "loop in the wrong place" bug as my earlier list-building attempt on DescNumbers, wearing a disguise. An iterator that returns the finished list on every call isn't an iterator — it's a function in iterator clothing. The fix was to move the two needed values onto `self`, return one per call, and let the *caller* (`list()`) do the collecting. Guarding with `self.count <= 0` also handles the `Fibonacci(0)` edge case cleanly — it returns an empty list rather than over-emitting.

## Challenge 4 - Fibonacci as a Generator

### Problem

Not really a bug — the challenge was understanding *why* the generator version is so much shorter than the class, and trusting that it does the same thing.

### Solution

Wrote the generator and compared it line-for-line against the class. The window-slide (`a, b = b, a + b`) is identical to the class version — that carried straight over. Everything else (the protocol methods, the stored counter, the manual `StopIteration`) disappears because `yield` handles pausing and resuming, and running off the end of the function raises `StopIteration` automatically.

### Lesson Learned

Writing the verbose iterator class *first* and the generator *second* was the right order — I understand what `yield` is hiding because I'd just written it all out by hand. The "stop after n" responsibility lives in a `self.count` I decrement manually in the class, but in `range(n)` in the generator — same job, different place.

# Biggest Lessons

- An iterator returns one value per call and remembers state between calls — the caller does the repeating. A loop inside `__next__` that builds the whole result is the wrong shape.
- "It runs without errors" and "it's correct" are still not the same thing (the recurring day006 lesson) — the fake Fibonacci ran and even printed plausible-looking values while being wrong on three separate counts.
- Generators are iterators with the boilerplate collapsed into `yield`. Building the same sequence both ways made the relationship concrete in a way that reading about it wouldn't have.
- The same off-by-one bug shows up at whichever endpoint the direction of counting exposes — and there's more than one valid way to fix it.
