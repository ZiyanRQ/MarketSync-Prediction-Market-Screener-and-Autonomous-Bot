# What I Built

Today was my first real API project, built from a blank file: a **crypto price tracker** that fetches live data from CoinGecko, lets me list the top coins or search for one by name or symbol, and displays the results through a reusable helper. The throughline was the **fetch → check → parse → search → display** skeleton — the same shape every API project (including the eventual bot) is built on.

## The core skeleton (single coin)

Started by proving the pipeline end-to-end with one coin:

```python
import requests

response = requests.get("https://api.coingecko.com/api/v3/simple/price?vs_currencies=usd&ids=bitcoin")
data = response.json()
print(f"Current Price of Bitcoin: ${data['bitcoin']['usd']:.2f}")
```

This locked in the four steps: `requests.get()` to ask, `.json()` to parse into a Python dict, navigating the nested structure (`data['bitcoin']['usd']` — two layers deep), and formatting with `:.2f`.

## The full version (list + search)

Then extended to the `/coins/markets` endpoint, which returns a *list* of coin dicts. The finished program:

- Fetches the top 250 coins by market cap.
- Checks `response.status_code == 200` **once** before using the data.
- Offers a list-or-search menu, with search by **name or symbol**.
- Correctly reports "not found" only after checking every coin (via `for...else`).
- Displays results through a single `display_coin(coin)` helper instead of repeated print blocks.

```python
def display_coin(coin):
    print(f"Name: {coin['name']}")
    print(f"Symbol: {coin['symbol']}")

    print(f"Market Cap: ${coin['market_cap']}")
    print(f"24h Change: {coin['price_change_percentage_24h']}%")
    print("\n")
```

# Programming Concepts Learned

Today I learned that:

- **A virtual environment (`.venv`) is per-project**, sits at the project root, and isolates that project's libraries. One venv per project — not one shared across all of them. `python -m venv .venv` creates it; you never edit inside it.
- **`ModuleNotFoundError` almost always means "right library, wrong Python"** — the library is installed somewhere, just not in the Python that's running the file. The fix is aligning the interpreter, not reinstalling.
- **On my setup, the ▶️ Run button uses Code Runner, which ignores the selected interpreter** and runs global Python (no libraries). Running via the terminal (`python main.py` with `(.venv)` showing) is the reliable way.
- **An API endpoint is just a URL** — pasting it into a browser shows the exact JSON my code will receive. Seeing the data's *shape* first is what makes the "dig out the value" step possible.
- **JSON nests** — `{"bitcoin": {"usd": 65114}}` is a dict inside a dict, so the price is two layers deep. The nesting scales: asking for more coins/currencies gives each its own labelled slot.
- **`requests` is cleaner than `urllib`** for the same job — no separate `import json`, no `.read()`; `.json()` parses in one step. It's what the rest of the Python world uses, so worth the muscle memory.
- **`for...else`**: a loop can have its *own* `else` that runs only if the loop finished *without* hitting a `break`. It's purpose-built for search — `break` when found, `else` fires only when nothing matched.
- **`if...else` under an `if` vs `else` under a `for` are completely different things** — the only visible difference is the indentation of `else`, but one means "this one item didn't match" and the other means "nothing matched after checking all." One indentation level changes the whole meaning.
- **print-functions vs return-functions**: a function that *prints* is called bare (`display_coin(coin)`); a function that *returns* a value is wrapped in print (`print(format_coin(coin))`). Wrapping a print-function in `print()` shows a stray `None` (its empty return value).
- **A function with no `return` returns `None`.**
- **`.env` + `.gitignore` is the pattern for API keys** — the key lives in `.env`, `.env` is gitignored so it never reaches GitHub, and code reads it via `load_dotenv()` + `os.getenv()`. Keys never go in the code as a literal or in a URL. (Not needed for this endpoint in the end, but set up the understanding.)

# Challenges

## Challenge 1 - ModuleNotFoundError: No module named 'requests'

### Problem

`requests` was installed, but running the file kept throwing `ModuleNotFoundError`. Reinstalling didn't help. Even Copilot couldn't fix it, because it's not a code problem.

### Solution

`pip show requests` confirmed it *was* installed — in `.venv`. The real cause: the ▶️ Run button (Code Runner) was running the file with my *global* Python, which doesn't have requests. Running `python main.py` in the activated `(.venv)` terminal used the right Python and it worked instantly — printing live Bitcoin data.

### Lesson Learned

`ModuleNotFoundError` = "right library, wrong Python." The library exists somewhere; the running interpreter just can't see it. Fix the interpreter/run-method, don't reinstall. On this machine, trust the terminal over the play button.

---

## Challenge 2 - The venv, OneDrive, and files in the wrong folders

### Problem

The venv creation hung partway (`KeyboardInterrupt`), and `main.py` ended up created *inside* `.vscode`, then confusion about whether code goes in the `Scripts` folder. All symptoms of not yet having a clear mental model of the project layout.

### Solution

The hang was OneDrive trying to sync the hundreds of tiny files a venv creates — dev projects don't belong in OneDrive. `main.py` belongs at the *project root*, next to `.gitignore` — never inside `.venv` (sealed machinery) or `.vscode` (editor config). Selecting the folder root before New File puts it in the right place.

### Lesson Learned

`.venv` and `.vscode` are sealed boxes I create but never open or edit. My code is one file sitting *next to* them, not inside them. And OneDrive fights with venvs — keep projects somewhere plain like `C:\Dev\`.

## Challenge 3 - The `else` that fired on the first coin

### Problem

My search loop had `else` indented under the `if`, so it printed "Cryptocurrency not found" on the *first* coin that didn't match — meaning any search that wasn't the very first coin in the list spammed "not found" as it scanned. It *looked* like it worked when I tested with "bitcoin" (the first coin), which hid the bug.

### Solution

Move `else` to align with `for`, not `if` (`for...else`) — so it runs only after the loop checks every coin without finding a match. The tell was testing with **"ethereum" instead of "bitcoin"**: the wrong version spammed "not found" before finding it; the fixed version came up clean.

### Lesson Learned

"It runs" ≠ "it's correct" — *again*. The bug was invisible until I tested the hard case (a coin that isn't first). `else` under `if` means "this one didn't match"; `else` under `for` means "nothing matched." One indentation level, entirely different meaning. Test with an input that *isn't* the easy case.

---

## Challenge 4 - The same fix applied unevenly

### Problem

I fixed the `for...else` in the name-search block but left the two symbol blocks with the bug — *and* had a duplicate `elif "symbol"` block that never ran (dead code). I said "fixed" when only one of the problems was actually fixed.

### Solution

Deleted the duplicate `elif`, and dedented the `else` in the remaining symbol block to match the corrected name block. Confirmed by testing the path I *hadn't* tested (search → symbol).

### Lesson Learned

Saying "fixed" after eyeballing isn't enough — check each item deliberately and test the paths I didn't take. A subtle one-indent bug and a near-identical duplicate block both hide easily at a glance. Testing one path only proves that one path.

---

## Challenge 5 - print(display_coin(coin)) and the stray None

### Problem

After building the `display_coin` helper, I called it as `print(display_coin(coin))`. Since the function already prints internally and returns nothing, the outer `print()` printed its empty return value — a stray `None` after every coin. I then over-corrected by making it `return` a *tuple* of strings, which printed as an ugly one-line `('Name: ...', 'Symbol: ...')`.

### Solution

Chose the "print-function" design: keep the internal `print()`s, call it bare as `display_coin(coin)`, no wrapper. A function whose job is to display is *called*, not printed.

### Lesson Learned

There's a difference between a function that **does** something (call it bare) and one that **returns** a value (wrap in print). Commas in parentheses make a tuple, not a joined string. `display_coin` acts — so `display_coin(coin)`, not `print(display_coin(coin))`.
